# 미결정 값

`docs/system-design/`에서 **아직 정해지지 않았거나 문서마다 다르게 적힌 값**을 모은다.

여기 있는 값은 판정 기준이 되지 못한다.
`code-guideline.md`의 항목이 "확정값과 일치하는가"를 묻는데, 확정값이 없거나 둘이면 판정할 수 없다.

두 부류가 섞이지 않게 나눈다.

| 부류 | 왜 못 정하는가 | 어떻게 정하는가 |
|------|----------------|-----------------|
| [1. 어긋난 값](#1-어긋난-값) | 문서마다 다르게 적혀 있다 | **읽고 고르면 된다.** 측정이 필요 없다 |
| [2. 비어 있는 값](#2-비어-있는-값) | 아직 측정하거나 실험하지 않았다 | 부하 시험, 스파이크, 리허설 |

1번은 지금 결정할 수 있고, 2번은 못 한다. 이 구분이 중요하다.

---

## 1. 어긋난 값

네 건이다. 게이트는 이것들을 `LGU-2/.github`의 `.github/llm-verify/known-conflicts.yml`에 `unresolved`로 등록해 두고, 관련 항목을 `CONFLICTING_BASELINE`으로 유보한다.
**한쪽을 골라 판정하지 않는다.** 그건 LLM이 팀의 결정을 대신 내리는 것이다.

정하면 `known-conflicts.yml`에서 해당 항목을 `resolved`로 바꾸거나 지운다.

### 1.1 readiness 그룹에 `db`를 넣는가

| 문서 | 위치 | 값 |
|------|------|-----|
| 앱과DB 장애대응구조 | 1.1절 | **철회.** 공유 의존성은 readiness에 넣지 않는다 |
| 기술 스택 확정 | 553~555행 | `readiness: include: db, diskSpace` |

```
초기 설계에서 ALB 헬스체크가 참조하는 readiness 그룹에 db를 포함하도록 적었다.
이는 잘못이며, 본 문서 4.1절의 근거로 철회한다. 공유 의존성은 readiness에 넣지 않는다.
                                        -- 앱과DB 장애대응구조 1.1절
```

**넷 중 가장 위험하다.** 철회 선언이 있는데 철회 대상이 다른 문서에 **실행 가능한 yaml 형태로** 살아 있어 그대로 복사될 수 있다.

같은 문서가 근거까지 적어 두었다.

| 대상 | 포함 여부 | 근거 |
|------|-----------|------|
| 인스턴스 로컬 상태 (디스크, 기동 완료) | 포함 | 이 인스턴스만의 문제이므로 빼면 해결된다 |
| 공유 의존성 (DB, 캐시, 외부 API) | 제외 | 모든 인스턴스가 동시에 빠져 상황이 악화된다 |

DB가 잠시 흔들리면 전 인스턴스가 동시에 대상 그룹에서 빠져 서비스가 통째로 끊긴다.

**결정할 것**: 기술 스택 확정 문서 553~555행을 `include: diskSpace`로 고칠 것인가.
**막고 있는 것**: `REL-5-01`, `REL-5-02`, `INF-4-01` 판정. 그리고 이 결정이 `intentional`로 등록된 "의도된 이탈" 처리를 가리고 있어, 게이트가 일반론 대신 확정값으로 판정하는 기능이 동작하지 않는다.

### 1.2 배포 중 확보 용량

| 문서 | 위치 | 값 |
|------|------|-----|
| 장애 대응 목표와 아키텍처 결정 | 239행 | 50% |
| 무중단 배포 롤링 | 19행 | 100% |
| 시스템 디자인 종합 | 353행 | 100% |

**같은 문서 안에서도 어긋난다.** 시스템 디자인 종합은 353행 표에 100%인데 380행 본문은 "배포 중 용량이 절반이 되는데"다.

무중단 배포 롤링 574행에는 두 값이 비교표로 나란히 있다(`50% | 100%`). 대상 그룹 스왑과 롤링을 비교한 표로 보이며, 그렇다면 롤링이 100%이고 50%는 이전 방식의 수치일 가능성이 크다.

**결정할 것**: 장애 대응 목표 239행을 100%로 고칠 것인가, 아니면 다른 전제인가.
**막고 있는 것**: 부하 시험 계획. 용량이 절반이면 시험 중 배포를 금지해야 하고 100%면 하지 않아도 된다.

### 1.3 배포와 롤백 소요 시간

| 문서 | 위치 | 값 |
|------|------|-----|
| 장애 대응 목표와 아키텍처 결정 | 240~241행 | 배포 3~4분, 롤백 3~4분 |
| 무중단 배포 롤링 | 20~21행 | 배포 6~8분, 롤백 6~8분 |

무중단 배포 롤링은 6~8분을 네 곳에서 반복한다(340행 롤백 재배포, 358행 연습, 452행 확인 항목, 506행 목표치). 일관성으로 보면 6~8분이 현재 값이다.

**두 배 차이라 장애 중 행동이 달라진다.** "3분이면 끝나니 기다리자"와 "8분 걸리니 지금 롤백을 결정하자"는 다른 판단이다.

**결정할 것**: 장애 대응 목표 240~241행을 6~8분으로 고칠 것인가.
**막고 있는 것**: 롤백 판단 시점, 인시던트 대응 절차의 시간 예산.

### 1.4 혼재 구간 길이

| 문서 | 위치 | 값 |
|------|------|-----|
| 장애 대응 목표와 아키텍처 결정 | 242행 | 약 2분 |
| 장애 대응 목표와 아키텍처 결정 | 281행 | 약 3분 |
| 무중단 배포 롤링 | 22행, 301행 | 약 1분 |
| 시스템 디자인 종합 | 356행 | 약 1분 |

**한 문서 안에서 2분과 3분으로 갈린다.** 둘 중 하나는 오타다.

이것이 실무에 가장 직접 걸린다. 혼재 구간은 **스키마 확장 후 축소에서 축소를 언제 해도 되는지**를 정한다.

```
롤링은 구버전과 신버전이 약 3분간 공존한다.
배치 주기가 그보다 짧으면 혼재 구간에 최소 한 번 걸린다.
                                        -- 장애 대응 목표 281절
```

1분으로 잡았는데 실제가 3분이면 **구버전 코드가 이미 없어진 컬럼을 읽는다.**

**결정할 것**: 1분인가 3분인가. 다수는 1분이지만 보수적으로 잡으려면 3분이다.
**막고 있는 것**: `INF-6-*` 스키마 축소 시점, 배치 주기 결정.

## 2. 비어 있는 값

측정하거나 실험해야 나오는 값이다. **읽어서 정할 수 없다.**

이 값에 걸린 점검 항목은 근거 판정(기록이 있는가)만 가능하고 일치 판정(값이 같은가)은 불가능하다.
"측정 전에는 경보 없이 관측만"이라는 규율을 그대로 적용한다.

### 2.1 부하 시험이 있어야 나오는 것

오토스케일링 설계 297~305행. 전부 `(미정)`이다.

| 값 | 어떻게 구하는가 |
|------|-----------------|
| 인스턴스당 처리 가능 RPS | 단계적 부하 증가 중 p99가 목표를 넘는 지점 |
| `ALBRequestCountPerTarget` 목표값 | 위 값의 60~70% |
| 인스턴스 기동 시간 | 증설부터 healthy까지 |
| 인스턴스 워밍업 | 기동 시간 + 여유 |
| 최대 인스턴스 수 | 산출식에 실측값 대입 |
| 배치 최대 실행 시간 | 배치 로그 |
| 수명주기 훅 제한 시간 | 배치 최대 실행 시간 + 여유 |
| 병목 위치 | 부하 증가 시 먼저 포화되는 구성요소 |

**병목 위치가 먼저다.** DB가 병목이면 앱을 늘려도 효과가 없으므로 오토스케일링 자체를 도입하지 않는다(`OPS-1-01`).

알람과 알림 설계 5.1, 5.2절의 임계값 5곳도 같다.

```
백업 미생성        LatestRestorableTime 지연 (미정)분
502 발생          (미정) 초과
RDS 여유 메모리    (미정) 미만
톰캣 스레드 사용률  (미정)% 초과
ConsumedLCUs      (미정) 초과
```

**발동하지 않는 알람은 없는 것과 같고, 잘못된 임계값의 알람은 그보다 나쁘다.**

시스템 디자인 종합 593~602행의 설정값 5종(socketTimeout, 풀 크기, 트랜잭션 타임아웃, 톰캣 스레드, ALB 임계값)도 부하 시험 후 확정한다.

### 2.2 조회하면 바로 나오는 것

| 값 | 어떻게 구하는가 | 왜 급한가 |
|------|-----------------|-----------|
| RDS `max_connections` | `SHOW VARIABLES LIKE 'max_connections'` | **커넥션 풀 크기와 인스턴스 상한의 전제다.** 지금 계산이 전부 가정 위에 있다 |

**부하 시험이 필요 없다.** 콘솔에서 1분이면 확인된다. 2번 부류 중 유일하게 지금 할 수 있는 것이다.

### 2.3 리허설이 있어야 나오는 것

| 값 | 현재 상태 |
|------|-----------|
| PITR 실측 RTO, RPO | 문서가 스스로 "근거 없는 목표치"라고 적고 있다 (60분, 5분) |

`OPS-1-12`가 이것을 점검한다.

### 2.4 스파이크가 있어야 정해지는 것

| 값 | 현재 상태 |
|------|-----------|
| QueryDSL 채택 여부 | 기술 스택 52행 **미확정**. Spring Boot 4 호환 미검증 |

```
착수 전에 스파이크로 검증한다. 엔티티 하나에 Q클래스를 생성하고
조인이 포함된 쿼리를 실행하면 30분 안에 판별된다.
여기서 막히면 대안을 택해야 하는데, 코드를 다 짠 뒤에 알면 되돌리기 어렵다.
                                        -- 기술 스택 확정 3.8절
```

**착수 전에 30분이면 끝난다.** 미루면 되돌리기 어려워진다.

### 2.5 아직 고르지 않은 것 (측정 불필요, 선택의 문제)

| 값 | 선택지 |
|------|--------|
| 추적(APM) 백엔드 | X-Ray 또는 Grafana Tempo |
| 알림 채널 | 이메일, Slack 등 |
| 개발 서버 유무 | 상시 가동 시 월 28~52 USD 추가 |
| 이중화 전환 시점 | `desired_capacity` 2로 상향. 월 22 USD 추가 |
| 분산 락 최종 채택안 | 두 구현 비교 실험 후 |
| Terraform 마이너 버전 | 구축 시점 최신 안정 버전 |

## 다음에 할 일

우선순위는 **막고 있는 것의 크기**로 정한다.

| 순위 | 무엇 | 드는 시간 | 막고 있는 것 |
|------|------|-----------|--------------|
| 1 | 1.1 readiness | 문서 한 줄 | 전 인스턴스 동시 이탈 위험, 게이트 기능 하나 |
| 2 | 1.4 혼재 구간 | 결정 하나 | 스키마 축소 시점 |
| 3 | 2.2 `max_connections` | 조회 1분 | 풀 크기 계산 전체 |
| 4 | 2.4 QueryDSL 스파이크 | 30분 | 착수 후에는 되돌리기 어려움 |
| 5 | 1.2, 1.3 | 문서 두 줄 | 시험 계획, 롤백 판단 |
| 6 | 2.1 부하 시험 | 시험 1회 | 오토스케일링, 알람 임계값 |

**1~5는 전부 하루 안에 끝난다.** 부하 시험만 별도 일정이 필요하다.
