비교 실험은 2대 이상이어야 의미가 있으므로, 배포 절차의 일시 증설을 활용해 실험 구간에만 2대를 확보한다.

## 2. 왜 분산 락이 필요한가

### 2.1 `@Scheduled`는 인스턴스마다 독립적으로 돈다

Spring의 `@Scheduled`는 애플리케이션 인스턴스 내부의 스레드 풀에서 동작한다. 스케줄러는 자신이 몇 번째 인스턴스인지 알지 못하고, 다른 인스턴스가 같은 작업을 하고 있는지도 모른다.

```java
@Component
public class ExpirationScheduler {

    @Scheduled(cron = "0 */5 * * * *")   // 5분마다
    public void expireOverdue() {
        // 인스턴스가 2대면 같은 시각에 2번, 3대면 3번 실행된다.
    }
}
```

가용성을 위해 인스턴스를 2대로 늘리는 순간, 별도 조치가 없으면 모든 배치가 2중으로 실행된다. **이 문제는 이중화의 부작용이며, 무중단을 지향하는 설계라면 반드시 함께 해결해야 한다.**

### 2.2 배치 유형별 중복 실행 피해

모든 배치에 락이 필요한 것은 아니다. 연산의 성격에 따라 피해가 전혀 다르다.

| 유형 | 연산 성격 | 중복 실행 시 | 심각도 | 락 필요 |
|------|-----------|--------------|--------|---------|
| 멱등 전이형 | 상태를 특정 값으로 덮어씀 | 같은 결과. 무해 | 낮음 | 불필요 |
| 재계산형 | 원본에서 값을 다시 계산해 덮어씀 | 같은 결과. 자원 낭비만 | 낮음 | 선택 |
| 누적 연산형 | 수량이나 잔액을 증감 | **오차가 누적되어 남음** | 치명적 | 필수 |
| 외부 부수효과형 | 알림 발송, 결제 요청, 파일 전송 | 외부에 이중 요청 | 높음 | 필수 |
| 순번 발급형 | 시퀀스나 채번 | 번호 중복 또는 건너뜀 | 높음 | 필수 |

예시로 옮기면 이렇다.

| 배치 예시 | 유형 | 중복 시 결과 |
|---|---|---|
| 만료 상태 일괄 전이 (`status = EXPIRED`) | 멱등 전이형 | 무해 |
| 통계 집계 테이블 갱신 | 재계산형 | 무해, CPU 낭비 |
| 만료 처리 후 자원 반환 (수량, 좌석, 한도 복원) | 누적 연산형 | **반환이 두 번 일어나 값이 부풀려짐** |
| 확정 처리 후 적립금 지급 | 누적 연산형 | **이중 지급** |
| 미발송 알림 재시도 | 외부 부수효과형 | 중복 발송 |
| 정산 번호 채번 | 순번 발급형 | 번호 충돌 |

**핵심은 세 번째 행이다.** 상태 전이만 보면 두 번 다 같은 값이라 무해해 보이지만, 그 전이에 딸린 누적 연산은 두 번 실행되면 그만큼 값이 커진다.

이 오차는 **발생 시점에 아무 신호도 내지 않는다.** 예외도, 오류 로그도, 실패 응답도 없다. 증상은 며칠 뒤 무관해 보이는 다른 트랜잭션에서 나타난다.

```
14:00  배치 중복 실행으로 자원 수량이 +3 부풀려짐
14:00  오류 없음. 예외 없음. 로그 정상
       사용자 화면에는 3개가 더 있는 것으로 표시됨
       ... 며칠간 정상 거래 계속 ...
17:20  그 3개를 소비하려는 요청이 실패
17:20  "자원 부족" 오류  <- 원인을 가리키지 않는 증상
```

원인이 발생한 시점과 증상이 나타난 시점이 멀고, 증상의 형태가 원인과 달라 추적이 매우 어렵다. **이 시간차가 곧 복구 난이도다.** 사고 직후면 되돌릴 수 있지만, 며칠 지나면 그 사이 정상 거래가 쌓여 되돌릴 방법이 사실상 없어진다.

감지 수단은 백업과 복원 문서 8절의 정합성 검증 배치이며, 대응 절차는 알람과 알림 설계 문서 5.4절에 있다.

### 2.3 피해 시나리오 상세

만료 처리 후 자원을 반환하는 배치를 예로 든다. 흐름은 세 단계다.

1. 만료 조건에 해당하는 레코드를 찾는다
2. 상태를 `EXPIRED`로 바꾼다
3. 점유했던 자원(수량, 좌석, 한도 등)을 되돌린다

인스턴스 A와 B가 동시에 실행하면 다음과 같이 흐른다.

```
시각  인스턴스 A                       인스턴스 B
t0    레코드 1001 조회 (PENDING)       레코드 1001 조회 (PENDING)
t1    status = EXPIRED 로 갱신
t2                                      status = EXPIRED 로 갱신 (덮어쓰기, 무해해 보임)
t3    자원 풀에 수량 + 3
t4                                      자원 풀에 수량 + 3
```

자원 수량이 실제보다 3만큼 부풀려진다. 상태만 보면 이상이 없어 검증 쿼리로도 잡히지 않는다.

### 2.4 락이 해결하는 것과 해결하지 못하는 것

분산 락은 "같은 시각에 하나의 인스턴스만 배치를 실행한다"를 보장하려는 장치다. 하지만 이는 **확률적 보장**이지 절대적 보장이 아니다. TTL 만료 구간에서는 두 인스턴스가 동시에 락을 가졌다고 믿는 상황이 발생한다.

따라서 층위는 이렇게 정리된다.

- 락은 **성능과 자원 낭비를 막는 1차 방어선**이다. 동일 작업이 N번 도는 것을 평상시에 막아 DB 부하와 외부 호출을 줄인다.
- 데이터 정합성의 **최종 보루는 락이 아니라 연산 자체의 멱등성**이다.

두 층을 모두 갖추어야 안전하다. 락만 믿는 설계는 락 저장소가 흔들리는 순간 데이터가 깨진다.

## 3. 락의 구조적 한계: TTL 만료와 fencing

분산 락은 락을 잡은 인스턴스가 죽었을 때 락이 영원히 남는 것을 막기 위해 TTL을 둔다. 이 TTL이 문제의 근원이다.

```
t0   인스턴스 A 가 TTL 30초로 락 획득, 배치 시작
t5   인스턴스 A 가 GC 정지 또는 컨테이너 일시정지로 멈춤
t30  락 TTL 만료
t31  인스턴스 B 가 락 획득, 배치 시작
t35  인스턴스 A 가 깨어나서 "나는 락을 가지고 있다"고 믿고 작업 계속
     -> A 와 B 가 동시에 실행 중
```

TTL을 길게 잡으면 인스턴스가 진짜 죽었을 때 복구가 늦어지고, 짧게 잡으면 위 상황의 확률이 올라간다. 이 트레이드오프는 어떤 락 구현을 쓰든 사라지지 않는다. Redis든 RDBMS든 동일하다.

완화 수단이 fencing token이다. 락을 획득할 때마다 단조 증가하는 번호를 발급하고, 보호 대상 자원이 자신이 본 마지막 토큰보다 작은 토큰의 쓰기를 거부하게 한다.

```
A 가 획득 -> fence_token = 41
B 가 획득 -> fence_token = 42
A 가 뒤늦게 41 을 들고 쓰기 시도 -> 자원이 이미 42 를 봤으므로 거부
```

완전히 적용하려면 모든 쓰기 경로가 토큰을 검사해야 해서 도메인 코드가 복잡해진다. 본 설계에서는 fencing token을 **발급하고 로그에 남겨 관측용으로만 쓰고**, 실제 방어는 다음 절의 조건부 UPDATE로 처리한다.

## 4. 최종 방어선: 조건부 UPDATE 멱등화

락이 뚫려도 데이터가 깨지지 않게 하려면, 상태 전이를 원자적 조건부 UPDATE로 수행하고 그 결과로 이후 동작을 분기해야 한다.

```java
@Transactional
public void expire(long recordId, Instant now) {
    // 상태 전이를 조건부 UPDATE 로 수행한다.
    // 이미 다른 인스턴스가 처리했다면 affected rows 는 0 이 된다.
    int transitioned = jdbcTemplate.update("""
            UPDATE reservation
               SET status = 'EXPIRED', updated_at = ?
             WHERE id = ? AND status = 'PENDING'
            """, Timestamp.from(now), recordId);

    if (transitioned == 0) {
        return;   // 누적 연산도 하지 않고 즉시 종료한다.
    }

    statusHistoryRepository.append(recordId, Status.EXPIRED, ChangedBy.BATCH);
    resourceService.release(recordId);   // 자원 반환은 전이에 성공한 쪽만 수행
}
```

핵심은 세 가지다.

1. **조회 후 판단하지 않는다.** `if (record.getStatus() == PENDING)` 형태로 먼저 확인하고 나중에 갱신하면 그 사이에 다른 인스턴스가 끼어든다. 갱신 손실 패턴 그대로다.
2. **누적 연산을 전이 성공 여부에 종속시킨다.** 전이가 원자적인 한, 누적 연산도 정확히 한 번 일어난다.
3. **전이와 누적 연산이 같은 트랜잭션 안에 있다.** 전이만 커밋되고 반환이 실패하면 자원이 영영 돌아오지 않는다.

외부 부수효과형 배치는 조건부 UPDATE로 먼저 처리 중 상태를 선점한 뒤 외부를 호출한다.

```java
// 발송 전에 상태를 선점한다. 선점에 실패하면 다른 인스턴스가 이미 집어 든 것이다.
int claimed = jdbcTemplate.update("""
        UPDATE notification
           SET status = 'SENDING', claimed_at = ?
         WHERE id = ? AND status IN ('PENDING', 'RETRY')
        """, Timestamp.from(now), notificationId);

if (claimed == 0) {
    return;
}
channel.send(notificationId);
```

발송 후에 상태를 바꾸면 그 사이에 다른 인스턴스가 같은 행을 집어 든다. 순서가 반대여야 한다.

## 5. 교체 가능한 락 설계

두 구현을 비교하려면 배치 코드가 락 구현을 몰라야 한다. 의존 역전을 적용한다.

```java
public interface DistributedLock {

    Optional<LockHandle> tryAcquire(String name, Duration ttl);

    void release(LockHandle handle);
}

public record LockHandle(String name, String owner, long fenceToken, Instant until) {}
```

배치는 이 인터페이스만 의존한다.

```java
@Component
public class ExpirationScheduler {

    private static final String LOCK_NAME = "expiration";
    private static final Duration LOCK_TTL = Duration.ofMinutes(4);

    private final DistributedLock distributedLock;
    private final ExpirationService service;

    public ExpirationScheduler(DistributedLock distributedLock, ExpirationService service) {
        this.distributedLock = distributedLock;
        this.service = service;
    }

    @Scheduled(cron = "0 */5 * * * *")
    public void run() {
        Optional<LockHandle> handle = distributedLock.tryAcquire(LOCK_NAME, LOCK_TTL);
        if (handle.isEmpty()) {
            return;   // 다른 인스턴스가 수행 중이다.
        }
        try {
            service.expireOverdue(handle.get().fenceToken());
        } finally {
            distributedLock.release(handle.get());
        }
    }
}
```

TTL은 배치 주기(5분)보다 짧게 잡는다. TTL이 주기보다 길면 정상 종료 후 다음 주기에 락이 남아 있어 배치가 건너뛰어진다.

구현체 전환은 프로퍼티 하나로 처리한다. 컨테이너 환경 변수만 바꿔 재기동하면 되므로 실험 진행이 쉽다.

```java
@Component
@ConditionalOnProperty(name = "app.lock.provider", havingValue = "mysql")
public class MysqlDistributedLock implements DistributedLock { /* 6절 */ }

@Component
@ConditionalOnProperty(name = "app.lock.provider", havingValue = "redis")
public class RedisDistributedLock implements DistributedLock { /* 7절 */ }
```

## 6. MySQL 기반 구현

### 6.1 스키마

```sql
CREATE TABLE scheduler_lock (
    lock_name   VARCHAR(64)  NOT NULL,
    locked_by   VARCHAR(128) NOT NULL,
    locked_at   DATETIME(3)  NOT NULL,
    lock_until  DATETIME(3)  NOT NULL,
    fence_token BIGINT       NOT NULL DEFAULT 0,
    PRIMARY KEY (lock_name)
) ENGINE = InnoDB;

INSERT IGNORE INTO scheduler_lock (lock_name, locked_by, locked_at, lock_until, fence_token)
VALUES ('expiration', '', '1970-01-01 00:00:00.000', '1970-01-01 00:00:00.000', 0);
```

행을 미리 만들어 두면 획득 로직이 UPDATE 하나로 끝난다. INSERT와 UPDATE를 분기하면 경합 시 중복 키 예외 처리가 추가로 필요해진다.

### 6.2 획득과 해제

```java
public class MysqlDistributedLock implements DistributedLock {

    private static final String ACQUIRE_SQL = """
            UPDATE scheduler_lock
               SET locked_by = ?, locked_at = ?, lock_until = ?, fence_token = fence_token + 1
             WHERE lock_name = ? AND lock_until <= ?
            """;

    private static final String RELEASE_SQL = """
            UPDATE scheduler_lock
               SET lock_until = ?
             WHERE lock_name = ? AND locked_by = ? AND fence_token = ?
            """;

    private final JdbcTemplate jdbcTemplate;
    private final Clock clock;
    private final String owner;   // 컨테이너 ID 등 인스턴스 식별자

    public MysqlDistributedLock(JdbcTemplate jdbcTemplate, Clock clock, String owner) {
        this.jdbcTemplate = jdbcTemplate;
        this.clock = clock;
        this.owner = owner;
    }

    @Override
    public Optional<LockHandle> tryAcquire(String name, Duration ttl) {
        Instant now = clock.instant();
        Instant until = now.plus(ttl);

        int updated = jdbcTemplate.update(ACQUIRE_SQL,
                owner, Timestamp.from(now), Timestamp.from(until), name, Timestamp.from(now));

        if (updated == 0) {
            return Optional.empty();
        }

        Long token = jdbcTemplate.queryForObject(
                "SELECT fence_token FROM scheduler_lock WHERE lock_name = ?", Long.class, name);
        return Optional.of(new LockHandle(name, owner, token, until));
    }

    @Override
    public void release(LockHandle handle) {
        // 만료 시각을 과거로 되돌려 즉시 해제한다.
        // locked_by 와 fence_token 을 함께 대조해, 이미 남이 잡은 락을 푸는 것을 막는다.
        jdbcTemplate.update(RELEASE_SQL,
                Timestamp.from(Instant.EPOCH), handle.name(), handle.owner(), handle.fenceToken());
    }
}
```

### 6.3 주의사항

- **락 획득 트랜잭션과 배치 작업 트랜잭션을 분리한다.** 같은 트랜잭션에 묶으면 배치가 도는 내내 `scheduler_lock` 행의 잠금이 유지되고 커넥션도 점유된다.
- **시각 기준을 애플리케이션 `Clock`으로 통일한다.** `NOW()`와 `Instant.now()`를 섞으면 DB 시각과 인스턴스 시각이라는 두 기준이 공존한다. 인스턴스 간 시계 오차가 TTL 판정에 그대로 반영되므로 EC2에서는 Amazon Time Sync Service로 시각을 맞춘다.
- **`SELECT ... FOR UPDATE`로 구현하지 않는다.** 락을 잡으려고 또 다른 락을 잡는 구조가 되어, 대기 인스턴스가 커넥션을 붙잡고 늘어진다.
- **검증된 라이브러리도 선택지다.** ShedLock의 JdbcTemplateLockProvider가 같은 원리로 동작한다. 직접 구현하는 이유가 학습이나 실험이 아니라면 라이브러리를 쓰는 편이 안전하다.

## 7. Redis 기반 구현

### 7.1 획득과 해제

`SET key value NX PX ttl` 한 번으로 "없으면 넣기"와 "만료 설정"이 원자적으로 처리된다.

```java
public class RedisDistributedLock implements DistributedLock {

    private static final String UNLOCK_LUA = """
            if redis.call('get', KEYS[1]) == ARGV[1] then
                return redis.call('del', KEYS[1])
            else
                return 0
            end
            """;

    private final StringRedisTemplate redisTemplate;
    private final Clock clock;
    private final String owner;

    public RedisDistributedLock(StringRedisTemplate redisTemplate, Clock clock, String owner) {
        this.redisTemplate = redisTemplate;
        this.clock = clock;
        this.owner = owner;
    }

    @Override
    public Optional<LockHandle> tryAcquire(String name, Duration ttl) {
        String key = "lock:" + name;
        String value = owner + ":" + UUID.randomUUID();

        Boolean acquired = redisTemplate.opsForValue().setIfAbsent(key, value, ttl);
        if (!Boolean.TRUE.equals(acquired)) {
            return Optional.empty();
        }

        Long token = redisTemplate.opsForValue().increment("fence:" + name);
        return Optional.of(new LockHandle(name, value, token, clock.instant().plus(ttl)));
    }

    @Override
    public void release(LockHandle handle) {
        // 소유자 확인과 삭제를 Lua 로 원자화한다.
        RedisScript<Long> script = RedisScript.of(UNLOCK_LUA, Long.class);
        redisTemplate.execute(script, List.of("lock:" + handle.name()), handle.owner());
    }
}
```

### 7.2 주의사항

- **`DEL`만으로 해제하지 않는다.** 내 락이 이미 만료되어 다른 인스턴스가 잡은 상태에서 `DEL`을 날리면 남의 락을 푸는 셈이 된다.
- **단일 노드에서는 RedLock을 쓰지 않는다.** 다중 노드 알고리즘의 전제가 성립하지 않는다.
- **Redis 장애 시 동작을 명시적으로 코딩한다.** 이것이 비교 실험의 핵심 관찰 지점이다.

  | 정책 | 동작 | 대가 |
  |---|---|---|
  | fail-closed | 예외 시 배치를 실행하지 않음 | Redis가 죽으면 배치가 멈춤 |
  | fail-open | 락 없이 실행 | 중복 실행 위험 |
  | fallback | MySQL 락으로 전환 | 복잡도 상승 |

  기본값은 fail-closed로 두고, 실험에서 세 동작의 결과를 각각 관측한다.
- **fence token 키에 만료를 두지 않는다.** 만료되면 카운터가 0으로 되돌아가 단조 증가가 깨진다. Redis 노드가 소실되면 이 카운터도 사라지므로, Redis 락은 fencing 보장이 구조적으로 약하다.

## 8. 비교 실험 설계

### 8.1 가설

| 번호 | 가설 |
|------|------|
| H1 | 정상 상태에서는 두 구현 모두 중복 실행이 0건이다 |
| H2 | 컨테이너 일시정지로 TTL을 넘기면 두 구현 모두 중복 실행이 발생한다 |
| H3 | 중복 실행이 발생해도 조건부 UPDATE 방어가 있으면 데이터 손상은 0건이다 |
| H4 | 저장소 장애 시 실패 방향이 다르다. MySQL 락은 배치 자체가 중단되고, Redis 락은 설정한 정책에 따라 갈린다 |
| H5 | 락 획득 지연은 Redis가 짧지만, 5분 주기 배치에서는 실질 차이가 없다 |

H3과 H4가 실질적 목적이다. H1과 H5는 확인용이다.

### 8.2 측정 지표

| 지표 | 정의 | 수집 방법 |
|------|------|-----------|
| 중복 실행 건수 | 동일 `scheduled_at`에 대해 배치 시작 로그가 2건 이상 | 구조화 로그(job_name, scheduled_at, instance_id, fence_token) |
| 락 획득 지연 | `tryAcquire` 호출부터 반환까지 | Micrometer 타이머 |
| 락 획득 실패율 | 실패 횟수 / 전체 시도 | Micrometer 카운터 |
| 상태 전이 중복 | 같은 레코드에 동일 전이가 2건 이상 | 검증 SQL(8.5절) |
| 누적 값 오차 | 배치 후 값과 기대값의 차이 | 검증 SQL(8.5절) |
| 배치 미실행 | 주기가 지났는데 실행 로그가 없음 | 로그 부재 감지 알람 |

### 8.3 장애 주입 시나리오

Docker를 쓰므로 주입 수단이 명확하다.

| 시나리오 | 주입 명령 | 관찰 대상 |
|----------|-----------|-----------|
| S1 정상 | 없음 | H1, H5 |
| S2 인스턴스 급사 | `docker kill app-1` | 락이 TTL 후 정상 해제되는지 |
| S3 인스턴스 정지 후 복귀 | `docker pause app-1` 후 TTL 초과 시점에 `docker unpause` | H2, H3 |
| S4 락 저장소 단절 | `docker network disconnect` 또는 보안 그룹 차단 | H4 |
| S5 시계 오차 | 컨테이너 시각 수동 조정 | TTL 판정 왜곡 |
| S6 부하 중첩 | k6 부하 중 S3 반복 | 커넥션 풀 경합 포함 관찰 |
| S7 롤링 배포 중첩 | 혼재 구간에 배치 주기 정렬 | 두 버전 동시 실행 안전성 |

S6은 처리 대상 데이터를 대량 생성한 뒤 S3를 반복한다. 처리 대상이 많을수록 배치 실행 시간이 길어져 TTL 초과 확률이 올라가므로 중복 실행을 재현하기 좋다.

S7은 실험이 아니라 **매 배포마다 실제로 일어나는 상황**이다. 롤링 배포의 혼재 구간(약 2분) 동안 구 버전과 신 버전이 모두 실제 트래픽을 처리하며, 배포가 중단되면 이 구간이 무기한 지속된다.

**두 버전이 모두 활성이므로 어느 한쪽의 배치만 선택적으로 멈출 수단이 없다.** 따라서 본 문서 4절의 조건부 UPDATE가 유일한 방어선이 된다.

### 8.4 실험 절차

각 조합(락 구현 2가지 x 시나리오 7가지)에 대해 다음을 수행한다.

1. DB를 알려진 상태로 초기화하고 기준 스냅샷을 저장한다
2. `app.lock.provider` 환경 변수를 설정하고 인스턴스 2대를 기동한다
3. k6로 처리 대상 데이터를 생성한다
4. 배치 주기를 최소 6회 관측할 때까지 대기한다(30분)
5. 해당 시나리오의 장애를 주입한다
6. 검증 SQL을 실행하고 지표를 기록한다
7. 환경을 초기화한다

동일 조합을 3회 반복해 재현성을 확인한다. 동시성 버그는 특정 타이밍에서만 나타나므로 1회 관측으로 결론을 내리지 않는다.

### 8.5 검증 SQL

상태 전이 중복 검출:

```sql
SELECT target_id, to_status, COUNT(*) AS transition_count
FROM status_history
WHERE to_status = 'EXPIRED'
  AND changed_by = 'BATCH'
GROUP BY target_id, to_status
HAVING COUNT(*) > 1;
```

누적 값 오차 검출(실험 시작 시 저장한 스냅샷과 대조):

```sql
SELECT r.id,
       r.quantity      AS actual_quantity,
       s.expected_quantity,
       r.quantity - s.expected_quantity AS diff
FROM resource_pool r
JOIN experiment_snapshot s ON s.resource_id = r.id
WHERE r.quantity <> s.expected_quantity;
```

외부 부수효과 중복 검출:

```sql
SELECT target_id, COUNT(*) AS send_count
FROM notification_log
WHERE status = 'SENT'
GROUP BY target_id
HAVING COUNT(*) > 1;
```

세 쿼리가 모두 0행을 반환해야 H3이 성립한다.

### 8.6 판정 기준

| 판정 | 조건 |
|------|------|
| 채택 가능 | S1에서 중복 실행 0건이고, S2부터 S7까지 전 구간에서 데이터 손상 0건 |
| 조건부 채택 | 데이터 손상은 0건이나 특정 시나리오에서 배치가 장시간 미실행 |
| 기각 | 어떤 시나리오에서든 데이터 손상이 1건이라도 발생 |

기각 판정이 나오면 락 구현을 바꾸는 것이 아니라 **조건부 UPDATE 방어에 구멍이 있다는 뜻**이므로, 도메인 코드를 먼저 고친다. 락 교체로 해결하려 들면 같은 문제가 다른 타이밍에서 재발한다.

## 9. 실험 환경 구성

로컬 재현용 Compose 구성은 운영과 동일한 버전을 사용한다.

```yaml
services:
  mysql:
    image: mysql:8.4
    environment:
      MYSQL_ROOT_PASSWORD: ${MYSQL_ROOT_PASSWORD}
      MYSQL_DATABASE: ${DB_NAME}
    command: --character-set-server=utf8mb4 --collation-server=utf8mb4_0900_ai_ci

  redis:
    image: redis:7.0-alpine
    command: redis-server --appendonly no

  app-1:
    image: ghcr.io/${GITHUB_OWNER}/${APP_NAME}:${TAG}
    environment:
      APP_LOCK_PROVIDER: ${LOCK_PROVIDER}
      APP_INSTANCE_ID: app-1
    depends_on: [mysql, redis]

  app-2:
    image: ghcr.io/${GITHUB_OWNER}/${APP_NAME}:${TAG}
    environment:
      APP_LOCK_PROVIDER: ${LOCK_PROVIDER}
      APP_INSTANCE_ID: app-2
    depends_on: [mysql, redis]
```

Redis 이미지는 `7.0-alpine`으로 고정한다. ElastiCache 엔진 7.1이 Redis OSS 7.0과 호환되므로, 7.2 이상 이미지를 쓰면 운영과 동작이 어긋난다.

통합 테스트는 Testcontainers로 같은 이미지를 띄운다. 두 인스턴스 동시 실행을 테스트로 재현하려면 스케줄러를 끄고 배치 진입점을 두 스레드에서 직접 호출한다.

## 10. 프로젝트 적용 체크리스트

| 항목 | 확인 |
|------|------|
| 배치 목록을 2.2절 유형으로 분류했는가 | 누적 연산형과 외부 부수효과형만 락이 필수 |
| 락 이름을 배치별로 분리했는가 | 하나의 락으로 모든 배치를 묶으면 불필요한 직렬화 발생 |

| 스케일 인 시 배치 중단을 막는 장치가 있는가 | 오토스케일링 도입 시 필수. 오토스케일링 설계 문서 5절 |
| 배포 중단 시 혼재 상태를 감지하는가 | 무기한 지속되면 위험이 누적 |

## 11. 요약

1. 인스턴스를 2대 이상 운영하면 `@Scheduled` 배치는 인스턴스 수만큼 중복 실행된다.
2. 위험한 것은 누적 연산형과 외부 부수효과형 배치다. 멱등 전이형은 락 없이도 안전하다.
3. 분산 락은 TTL 만료 구간에서 뚫릴 수 있으므로 절대적 보장이 아니다.
4. 정합성의 최종 보루는 락이 아니라 조건부 UPDATE에 의한 멱등화다.
5. MySQL 락과 Redis 락은 정상 상태에서 차이가 거의 없고, 저장소 장애 시의 실패 방향에서 갈린다. 이 차이를 실측하는 것이 실험의 목적이다.
